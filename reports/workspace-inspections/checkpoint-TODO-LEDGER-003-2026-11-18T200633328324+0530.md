## 4. TODO-LEDGER-003 — authorization reference source findings

### 4.1 A0 / A1 / A2 semantics

A0, A1 and A2 appear as enum values in:
- schemas/authorization-reference.schema.json
- schemas/task.schema.json
- schemas/delegation-ledger.schema.json
- schemas/message.schema.json

The inspected normative docs/swarm-execution-mandate.md, lease runtime, task bootstrap contract and application source do not define their meanings, ordering, inheritance or relationship to READ / PROPOSE / MUTATE.

tests/fixtures/authorization-reference.json contains one valid example with level A1 and permissionClass READ. A fixture example is not an authoritative level definition. Its comment cites INTERFACE-001 and SC-14; the scoped repository search found fixture references but no corresponding INTERFACE-001 specification document.

**Design constraint:** treat the level as an opaque enumerated label. Do not rank A0/A1/A2, infer a permission from a level, or silently map a level to a permission class. Any authorization decision requiring level semantics must fail closed until an authoritative policy defines them.

### 4.2 Normative wording conflict

The current checkpoint operating rule and TODO-LEDGER-002 design separate readiness from authority: maturity and proposal acceptance do not authorize mutation; mutation requires an exact operator grant plus a current task-scoped writer lease/fencing generation.

However, docs/swarm-execution-mandate.md says at lines 12 and 94 that the reviewed planning gate/readiness “authorizes” the exact allowlist. This wording conflicts with the explicit-grant separation in the current operating model and TODO-LEDGER-002.

This is a policy reconciliation item, not permission to reinterpret either record. No schema or runtime change should proceed until the project policy owner resolves the wording and establishes the authoritative rule.

### 4.3 Current schema shape and gaps

schemas/authorization-reference.schema.json requires ref, level, permissionClass, scope, source and provenanceClass. grantedBy and expiresAt are optional. The schema does not bind the grant to a project, task, plan revision/digest, exact repository paths and operations, budget, egress policy, issuer identity, authenticated operator proof, issue time, revocation event or consumption/replay state. Scope is an array of strings without a defined grammar or matching semantics.

The representations are inconsistent:
- work-item.schema.json requires authorizationRef as a string but does not link it to the authorization-reference schema.
- task.schema.json requires permissionClass, while authorizationRef is optional.
- delegation-ledger.schema.json requires authorizationLevel, permissionClass and scope, while authorizationRef is optional.
- message.schema.json carries a nested permission class and authorization level, but no grant reference or operator-grant identity.

The existing grantedBy display string and provenance enum are not, by themselves, proof that an authenticated operator made the decision.

### 4.4 Existing lease and mutation boundary

The current implementation has useful fencing primitives, but no authorization-reference resolver:

- apps/api/src/db/projectWriterLeases.js requires a non-empty authorizationRef at acquisition and includes it in the lease binding digest. It does not resolve the reference to a grant record.
- assertCurrentWriterLease checks active status, expiry, fencing generation, current-lease pointer, project/task/owner bindings, digests and allowlist. It does not validate grant identity, expiry, revocation, permission class or plan digest.
- apps/api/src/projectWriterLease.js enforces repository anchors and file/path/operation allowlists, but the file mutation guard validates the lease rather than the authorization grant.
- apps/api/src/db/tasks.js checks the task-scoped lease environment and mutation capability for cURL AI Bridge task writes. It does not resolve an operator grant.
- apps/api/src/db/taskBootstrap.js accepts a non-empty authorization reference, stores it in an append-only bootstrap event and enforces generation/idempotency conditions; it does not resolve the reference.
- apps/api/src/database.js composes the lease store, task bootstrap, lease guard, tasks and proposals stores; no authorization resolver is composed.
- The live database has no task_authorizations, task_governance_events, task_execution_attempts or task_revisions tables.

The lease runtime is documented as a same-host SQLite coordinator, not multi-host distributed consensus. The lease is a serialization/fencing control, not an operator grant.

### 4.5 Existing task proposal flow

apps/api/src/db/taskProposals.js and apps/api/src/routes/proposals.js expose proposed, approved, rejected and rolled_back. Approval creates a task and marks the proposal approved; the proposal record has no authorization reference and the decision path performs no grant resolution. The normative mandate's reviewed and deferred states are not present in this route/store. Rollback calls tasks.deleteTask for the created task; TODO-LEDGER-002 already records the associated history-retention concern.

Static call-path observation: proposal approval passes the proposal's project to tasks.createTask; the cURL AI Bridge task insert calls assertManagedMutation without a task ID, while that guard requires a task ID. The cURL AI Bridge proposal path therefore appears to fail closed with writer_lease_task_scope_missing. This was inferred from source only; no route or test was executed.

That separate dispatch contract validates a Core-signed EdDSA permit with project/task/run/request/operation/input-digest bindings, timestamps, model/role restrictions and execution limits. The validator is documented as not yet wired to a runtime listener. ## 6. TODO-LEDGER-003 — proposed design contract (not approved)

### 6.1 Authority and level handling

1. Readiness, maturity, proposal acceptance, model output, worker output, quota availability and a writer lease are not operator authorization.
2. Mutation requires a valid explicit operator grant for the exact project, task, reviewed plan revision/digest, permission class, scope and limits, plus a current task-scoped writer lease and fencing generation.
3. A0/A1/A2 remain opaque until the authoritative policy owner defines each value and its relationship to permission classes. Unknown or unresolved level semantics block authorization decisions.

### 6.2 Grant identity and provenance

A future grant record should identify, without storing credentials:
- immutable grant ID and schema/policy version;
- issuing authority and stable operator principal/subject ID;
- trusted identity issuer and authentication-method/assertion reference;
- explicit operator decision/event ID and decision timestamp;
- project ID, task ID, plan revision and canonical plan digest;
- permission class and exact scope;
- budget ceiling and explicit egress policy;
- issued-at, not-before and expiry;
- usage mode and maximum consumptions, if bounded;
- append-only revocation/consumption event references;
- stable idempotency/replay key and provenance references.

grantedBy alone is insufficient. A worker, agent, model, external claim or task proposal cannot self-issue an operator grant. The allowed source × provenanceClass compatibility matrix must be defined by authoritative policy; do not invent it.

### 6.3 Reference parsing and resolution

Proposed transport rule: retain authorizationRef as an opaque, case-sensitive identifier that points to a canonical immutable grant record; do not embed executable policy in a free-form string and do not dereference arbitrary URLs or external paths.

A versioned parser/schema contract should:
- reject empty, malformed, unknown-version and non-canonical references;
- resolve only against a trusted project-scoped grant registry/store;
- validate the complete record against a versioned strict schema with no unknown fields;
- reject duplicate JSON keys, invalid Unicode, non-canonical timestamps and digest mismatches;
- verify that the resolved record's own ID equals the supplied reference;
- preserve legacy references as unresolved evidence rather than silently upgrading them.

A candidate reference grammar and canonical serialization profile remain design decisions for independent review; this report does not create a new schema.

### 6.4 Scope matching

A grant must be bound to and checked against:
- exact project and task;
- exact plan revision and digest;
- registered repository identity;
- exact normalized relative path and operation type for each file mutation;
- exact permission class;
- budget ceiling/units and remaining budget;
- explicit egress category/allowance.

Requested operations must be a subset of the grant. No implicit wildcard, parent-directory expansion, cross-project inheritance, operation widening or budget/egress default is allowed. Repository branch/HEAD anchors and the writer lease allowlist remain separate preconditions.

### 6.5 Time, revocation, consumption and replay

- Require canonical UTC issue/not-before/expiry timestamps and a policy-defined maximum lifetime.
- Validate time at every authorization boundary; expired, not-yet-valid or unverifiable clock state fails closed.
- Revocation is an append-only event; once observed, a grant cannot authorize a later operation.
- If one-shot or bounded-use grants are supported, consumption must be recorded atomically with the protected mutation decision and protected by a unique idempotency key.
- Replays return the recorded prior disposition only for the same exact operation identity; changed task, plan digest, operation or scope is a conflict.
- An ambiguous mutation outcome is not automatically retried or treated as unused authority.

### 6.6 Mutation boundary and writer-lease composition

The future resolver must run at the mutation boundary, not merely in a cooperative CLI or proposal route. In the same transaction/serialization boundary as a task or task-event write, it must verify:
1. trusted grant lookup and schema integrity;
2. authenticated operator issuer/provenance;
3. active, non-revoked, time-valid grant;
4. exact project/task/plan revision/digest;
5. permission class, path/operation scope, budget and egress;
6. exact equality between the grant reference and the lease's authorization reference;
7. current lease ID, task, owner, expiry, repository anchors, allowlist digest and fencing generation.

A lease without a valid grant fails; a grant without a current lease/fence fails. File writes must revalidate both grant and lease immediately before the irreversible rename/commit step. Lease acquisition itself must not turn a non-empty reference into a valid grant.

### 6.7 Fail-closed dispositions

At minimum distinguish:
- AUTH_REF_MISSING, AUTH_REF_MALFORMED, AUTH_REF_UNKNOWN, AUTH_SCHEMA_INVALID;
- AUTH_LEVEL_UNDEFINED, AUTH_POLICY_VERSION_UNKNOWN;
- AUTH_ISSUER_UNVERIFIED, AUTH_OPERATOR_UNVERIFIED, AUTH_PROVENANCE_CONFLICT;
- AUTH_PROJECT_MISMATCH, AUTH_TASK_MISMATCH;
- AUTH_PLAN_REVISION_MISMATCH, AUTH_PLAN_DIGEST_MISMATCH;
- AUTH_PERMISSION_MISMATCH, AUTH_SCOPE_MISMATCH;
- AUTH_BUDGET_EXCEEDED, AUTH_EGRESS_DENIED;
- AUTH_NOT_YET_VALID, AUTH_EXPIRED, AUTH_REVOKED;
- AUTH_ALREADY_CONSUMED, AUTH_REPLAY, AUTH_IDEMPOTENCY_CONFLICT;
- LEASE_MISSING, LEASE_EXPIRED, LEASE_REVOKED, LEASE_STALE_FENCE, LEASE_BINDING_MISMATCH;
- AUTH_UNVERIFIABLE.

Every such disposition blocks the mutation and records evidence without widening scope or retrying automatically.

### 6.8 Migration compatibility and acceptance tests

No migration is proposed in this checkpoint. If separately authorized later:
- preserve all existing task/proposal/lease/bootstrap/event IDs and history;
- do not reinterpret old approved, done, in_progress, non-empty auth references or lease rows as verified grants;
- classify unresolved legacy references as LEGACY_UNVERIFIED;
- use additive, versioned, append-only grant/revocation/consumption records;
- avoid destructive rebuilds, sequence resets, ID reuse and automatic backfills.

Acceptance coverage should include strict parser/schema validation; undefined A-level semantics; operator identity and provenance failures; wrong project/task/revision/digest; scope/path/operation widening; budget and egress violations; not-before/expiry/revocation; one-shot concurrent consumption; idempotent same-operation replay; changed-operation replay conflict; grant-without-lease; lease-without-grant; stale fencing generation; mutation-boundary race; proposal acceptance without authorization; legacy-row preservation; and no side effects on every rejected case.

### 6.9 Policy decisions still required

Before implementation, the policy owner must define:
1. exact A0/A1/A2 meanings and whether they are ordered;
2. allowed source × provenanceClass combinations;
3. the trusted operator identity/assertion mechanism;
4. canonical reference grammar and grant-record digest profile;
5. canonical scope/path/operation grammar;
6. budget units and egress categories;
7. maximum grant lifetime, clock-skew tolerance and default usage mode;
8. whether one-shot grants are required and how ambiguous outcomes are reconciled.

**Design status:** proposed contract only. A-level semantics and the planning-gate wording conflict remain unresolved. No schema, API, lease runtime, task, database or authorization record was changed.
