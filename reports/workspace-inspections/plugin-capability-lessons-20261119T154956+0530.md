### Hatchable guide facts and caveats
- MCP tool files are statically discovered under top-level `mcp/*.js`; filename and exported tool name must match. Tool schemas/descriptions must be statically extractable literal values. Tool handlers validate arguments themselves; the platform wraps JSON results in MCP text content and wraps thrown errors with `isError: true`.
- MCP grants are project-scoped: JWT audience is the project's MCP URL. The guide documents 1-hour access JWTs and 30-day refresh tokens whose fixed grant window is not extended by refresh; revocation invalidates both. These are Hatchable-specific documented values, not general OAuth constants.
- Hatchable's `access` guide distinguishes public, app-user, collaborator-member, admin and scheduler planes; edge enforcement occurs before the handler. It states app-user `user` access is not valid for MCP tools. The separate `expose-an-mcp-tool` guide lists `user | member | admin` in its example and says scheduler is invalid, but does not explain the `public` discrepancy. **UNRESOLVED DOCUMENTATION INCONSISTENCY:** do not infer the accepted MCP access enum from these two guides until clarified.
- Agent tool loops use a `maxSteps` cap. Function-style tools can be normalized across providers; provider-native tools pass through provider-specific shapes and reduce portability. The guide describes the tool loop as model call → tool execution → result → next step, with a terminal text response or max-step stop.
- Hatchable platform limits documented by `platform-constraints`: V8 isolate, 30 s CPU, 5 min wall clock, 128 MB memory, outbound fetch 30 s default / 55 s maximum, DB statement 5 s. These are Hatchable runtime limits only.
- Keyset pagination guide recommends deterministic cursors, a unique tie-breaker for non-unique sort keys, `LIMIT N+1`, and treating cursors as non-authentication data. Cursors may become invalid when ordering/schema changes.
- `connect-an-external-api` documents project-level provider credentials/tokens, account-level OAuth app credentials, separate credentials for separate projects/forks, optional explicit per-end-user connections, one-time OAuth state with a 10-minute TTL, and `SetupRequired` when no connection exists. It says provider rate limits remain provider-owned.
- `use-a-provider-directly` documents a Hatchable-specific AI gateway: BYOK credentials remain server-side; unsupported platform-key request fields can be refused with HTTP 412 before contacting the provider; setup-required and credit-limit refusals are distinct; null cost means unpriced, not free. It documents method gating for dangerous HTTP verbs. These semantics must not be generalized to unrelated providers.
- `inspect-llm-call-history` documents a platform usage ledger, ~60 s rollup caching, and an explicit `unpriced_calls` / `cost_is_complete` distinction. A null price is not zero cost.

## 7. Reusable lessons (evidence-tagged)

1. **FACT — separate catalog, tool exposure and account access.** The ChatGPT skill catalog was empty while 685 tools were exposed; Todoist/Gmail/Calendar tools were exposed while their named app-permission lookups said not installed. Hatchable's 57 platform skills are a separate catalog. Evidence: `skills__list`, `ALL_TOOLS`, Hatchable `list_skills`, app permission metadata.
2. **FACT — permission mode is not OAuth scope.** `Allow low-risk actions` and `Use my default` describe ChatGPT approval behavior, not provider account connectivity or token scopes. Evidence: Plugin Management tool description and structured permission results.
3. **FACT — stable identifiers and explicit scoping prevent accidental broad reads.** GitHub exact owner/repo + issue number, Dropbox file ID, Linear workspace/project query, and Remote Desktop device ID were used. Several other connectors explicitly warn that default list/search operations span whole accounts/workspaces. Evidence: tool schemas/descriptions and successful reads above.

## 8. cURL AI Bridge architecture implications

- Keep distinct entities for `ProviderConfig` (endpoint, credential owner, account/billing lane), `CLIInstance` (binary/version/device/cwd/config location), `Invocation` (exact model ID, arguments, timeout, request ID), `Session` (session/conversation identity and isolation policy), and `ModelDescriptor` (provider-native identifier, alias, catalogue source/version, capability set).
- Default to isolated sessions. Shared sessions require explicit same-provider/same-account compatibility evidence and an intentional policy flag; do not infer sharing from one CLI being authenticated.
- Keep exact provider model IDs separate from aliases. Validate against a provider-specific catalogue where supported; reject unknown IDs before dispatch. Provider-native tool definitions remain adapter extensions, not universal schema.
- Track credential identity, provider account, billing lane, quota bucket, entitlement evidence, and pricing evidence separately. Missing quota, null cost, or a visible model is UNKNOWN, never zero/free.
- Separate inference result, tool-loop result, orchestration task result, collaboration publication and terminal run state. A completed model response does not imply task synchronization or worker completion.
- Preserve cURL AI Bridge's existing coordination-only cloud protocol boundary. No dispatch, live inbox polling or inference was performed.

## 9. Regression-test candidates (PROPOSAL)

- Catalog entry exists / action exposed / authenticated read are three independent state variables; test all combinations including exposed-but-not-installed.
- Permission denial or missing auth must return a typed unavailable state without prompting for elevation or switching permission modes.
- Exact project/resource selectors must be required for account-wide search/list APIs; test no implicit global search.
- Cursor pagination must be opaque, provider-scoped, replay-safe and stable under inserts; ordering changes invalidate cursors explicitly.
- Duplicate asynchronous tool invocation must not occur while an earlier call is pending; terminal result retrieval must be separate from retry.
- Model aliases resolve to exact provider IDs with a catalogue version; unknown IDs fail before dispatch.
- Provider-native tool declarations are tagged nonportable and must not silently cross provider adapters.
- Unknown quota / unpriced usage blocks any free-only or budget-constrained dispatch.
- 412 setup/limit errors, 429 provider throttles, transient 5xx, cancellation and timeout are distinct terminal/retry classes; permanent configuration failures are not retried.
- Session isolation is default; intentional shared-session mode requires matching provider/account/session compatibility evidence.
- Inference completion, collaboration delivery and task terminal state are independently asserted and reconciled.
